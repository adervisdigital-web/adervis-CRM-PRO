## ✅ Выполнено — заход 19–26.07.2026 (SW v76 → v164)

### Безопасность: построчный аудит всех 21 Edge Function (26.07, `f73604b`..`1e930c1`)
Метод: `supabase db query --linked` — читает живые политики `pg_policies` и тела функций
через Management API, **не требует Docker** (в отличие от `db dump`). Три реальные находки:
- [x] **`calendar-feed` отдавал клиенту ВСЕ сделки агентства.** В режиме `?portal=` при
  пустом `client_portals.project_id` код падал в ветку «показать все проекты».
  Проверка живых данных: **0 из 12** порталов имели `project_id` → утечка работала
  ежедневно у всех. Клиент, подписавшийся на календарь своей сделки, видел названия и
  дедлайны сделок других клиентов этого агентства. **Самая серьёзная находка проекта.**
- [x] **`agency-notify` доверял `agencyId`/`briefData` из тела запроса** — `agencyId` открыто
  лежит в публичной ссылке бриф-формы, поэтому кто угодно мог слать агентству поддельные
  Telegram-уведомления «новый бриф» с произвольным текстом (вектор фишинга). Теперь
  принимает только `submissionId` и достаёт данные из БД сам.
- [x] **`telegram-notify` без лимита частоты** — любой триал-аккаунт мог использовать бота
  как открытый релей на произвольные `chat_id`. Добавлен счётчик с окном (30 сообщений/мин
  на агентство, миграция `20260726000001`) — не простой gate, т.к. рассылка легитимно шлёт
  пачку сообщений по одному на получателя.
- [x] Остальные 18 функций проверены построчно — уже безопасны (личность везде из
  проверенного JWT, платежи перепроверяются через API ЮKassa, cron защищён секретом).

## ⚠️ Технический долг
На 03.07.2026 закрыто найденное тогда (2 race condition, RPC-дыра, RLS performance);
`supabase db advisors --type security|performance` — чистые.

**Но:** аудит 26.07 показал, что советники **не видят дефектов логики** — ни одна из трёх
уязвимостей выше ими не ловилась. Поэтому «долг закрыт» больше не утверждается; вместо
этого в PLAN.md заведена процедура F35 — построчный аудит Edge Functions раз в квартал.

**Известный отложенный долг:** `client_portals` в RLS сравнивает `agency_id = auth.uid()`
напрямую, а не через `profiles.agency_id`. Сегодня безвредно (агентство = 1 пользователь),
сломается при появлении команды — чинить вместе с фичей ролей (пункт 34 в PLAN.md).
